## 2026-08-25 — Task 1.1 hardened XML loader + detection

- **D-024 XML DOM/XPath stack in core = `@xmldom/xmldom` 0.9.12 + `xpath` 0.0.34 (+ `zod` 4.4.3 for the T1 `format` schema).** Pure JS, versions per D-006. Hardening is parser-independent and runs on the raw text *before* any parser: size cap (20 MiB), **any `<!DOCTYPE` is rejected outright** (no DTD ⇒ no external entities, no billion laughs — regardless of which engine later re-parses the same text: Saxon-JS, xmllint-wasm), nesting-depth scan (256), then xmldom with `onError` → `XmlLoadError{code,line,column}`. Error codes `KONTOR-XML-{SIZE,DTD,DEPTH,MALFORMED}`. Saxon-JS was considered as sole parser+XPath (it is a runtime dep anyway) but rejected for the loader: weaker well-formedness diagnostics (no line/col) and heavier parse; it still re-parses `XmlDocument.text` for the transform.
- **D-025 `DetectedFormat` facets:** `profile` is a CII/ZUGFeRD-only concept — the bare `urn:cen.eu:en16931:2017` maps to `profile:"en16931"` for CII, `null` for UBL. The XRECHNUNG ZUGFeRD profile cannot be told apart from a plain XRechnung CII by the guideline ID; it is asserted from the PDF's XMP `fx:ConformanceLevel` (Task 1.2). XRechnung version + variant (`base|extension|cvd`) come from the CustomizationID using the same string keys as KoSIT `scenarios.xml` (D-017).
- **D-026 PDF extraction (Task 1.2) uses `pdf-lib` 1.17.1 low-level objects** (catalog `/Names/EmbeddedFiles` name tree + `/AF`, `PDFRawStream`), i.e. the same library as generation (D-022) — no second PDF parser. FlateDecode attachments are inflated with Node `zlib.inflateSync({ maxOutputLength })` so a decompression bomb is rejected before it materialises (`KONTOR-PDF-DECOMPRESS-SIZE`); other filters use pdf-lib's decoders behind a raw-size check. Encrypted PDFs are rejected (`KONTOR-PDF-ENCRYPTED`; detected by message as well as `instanceof`, because pdf-lib's CJS/ESM builds ship distinct class identities). Attachment choice: `factur-x.xml` > `zugferd-invoice.xml` > `xrechnung.xml`, else first embedded file whose bytes are XML with a CII/UBL root. The XMP `fx:ConformanceLevel` is authoritative for the ZUGFeRD profile (it is the only way to see the XRECHNUNG profile).
- **D-027 `InvoiceModel` is a plain typed object; the PRD §5.3 `{bt, value}` shape is an output projection.** Zod (`InvoiceModelSchema`) is the single source of truth and the TS type is inferred from it. A static path→BT/BG table (`model/bt-map.ts`) drives `toAnnotatedJson()` and the generated `docs/BT-COVERAGE.md` (`pnpm bt-coverage`, 164/164 core BTs mapped). Rationale: plausibility math and generation are far simpler on unwrapped fields; the annotated shape is only needed at the tool boundary. Amounts/quantities/percentages stay verbatim strings (decimal.js downstream). Parsers are data tables (`parse/ubl.ts`, `parse/cii.ts`) run by one generic XPath extractor; missing mandatory fields become `KONTOR-PARSE-MISSING` warnings instead of exceptions.

## 2026-08-25 — Task 2.1 plausibility layer

- **D-032 Money math: `decimal.js` 10.6.0 (MIT), cloned with `ROUND_HALF_UP`.** All Layer-3 arithmetic runs on a `Decimal.clone({ rounding: ROUND_HALF_UP, precision: 40 })` — kaufmännische Rundung on cents, never `Number`. Recomputations that involve rounding (line net = qty × price ÷ base qty; VAT = taxable × rate) use a two-tier tolerance: exactly 1 cent → `warning` (legitimate per-line vs. per-breakdown rounding), more → `error`. Pure sums (BT-106/109/110/112/115) are compared exactly. This is deliberately stricter than the official BR-CO-17, which tolerates ±1 currency unit — the €0.02 VAT fixture passes KoSIT but is flagged by Kontor.
- **D-033 IBAN/BIC via `ibantools` 4.5.4 (MIT/MPL-2.0 dual, MIT chosen); everything else hand-rolled.** `isValidIBAN` (mod-97 + per-country length/BBAN) and `isValidBIC`; only IBAN-shaped BT-84/BT-91 values are checked so national account numbers stay untouched. EU VAT-ID formats (27 + XI) are a regex table (VIES structures); unknown prefix → `warning`, known-prefix mismatch → `error`. Steuernummer: digit count ∈ {10, 11, 13}. Leitweg-ID: detected by shape only (numeric coarse part 2–12, optional fine part ≤ 30, two check digits, hyphen-separated) so plain buyer references such as `PO-2026-08` are never mistaken for one; check digits per ISO 7064 MOD 97-10 (`leitwegCheckDigits`, exported). No library exists for these and the specs are small and stable.
- **D-034 Plausibility never changes the official verdict.** `validateInvoice` reports `layers.plausibility` (`pass`/`fail`/`skipped`) and appends the findings, but `valid` only considers XSD/Schematron so KoSIT parity (89/89) is preserved. Findings carry JSON-pointer `location`s into the `InvoiceModel` (e.g. `/vatBreakdown/0/taxAmount`) rather than XPaths, because the checks run on the semantic model and must be syntax-neutral (UBL and CII). Duplicate detection is limited to caller-provided invoice numbers (no hashes, no persistence — the server stays stateless). `KONTOR-PLAUS-VAT-EXEMPTION-REASON` was dropped: BR-E-10/BR-AE-10 already cover it.

## 2026-08-25 — Task 2.2 audit_invoice

- **D-035 Audit report = header facts + verdict + recommendation + grouped findings; recommendation is a fixed decision table.** `auditInvoice` (core) runs parse + all three validation layers on one loaded document and builds `{ header, verdict, recommendation, rationale, findings: { structure, businessRules, plausibility }, stats, layers, timings, disclaimer }`. Recommendation: any fatal/error from XSD or Schematron → **reject** (the KoSIT validator would reject it); otherwise any error-level `KONTOR-PLAUS-*` (incl. `DUPLICATE`) → **review**; otherwise **accept** (warnings are listed, never block). The rationale names up to three rule ids so the model can quote them. The verdict keeps the `validate_invoice` convention (`info` never demotes `valid`). The header puts BG-23 (`taxBreakdown`), totals, Leitweg-ID/buyer reference and IBANs up front (Desktop finding F9); the text rendering (`renderAuditText`, DE/EN, decimal comma in DE) is deterministic and golden-tested via `toMatchFileSnapshot` with timings stripped (`test/golden/` is excluded from Biome so the snapshots stay byte-stable). KB enrichment (`enrichFinding`) and `DISCLAIMER` moved into core so `validate_invoice` and `audit_invoice` share them. Server: `SERVER_INSTRUCTIONS` are sent on initialize and every document tool description carries the `file_path`-vs-`content_base64` convention (F5); `resolveInput` distinguishes `ENOENT` from `EACCES`/`EPERM` with the macOS Privacy & Security hint (F10). F7 (Desktop never hands attachment bytes to stdio servers) stays documented-only until Streamable HTTP (Task 3.1).

## 2026-08-25 — Task 2.3 generate_invoice

- **D-036 `InvoiceInput` is flat and LLM-shaped; amounts are derived, never accepted.** The input carries only business facts (parties, lines with quantity × net price, VAT category/rate, payment, references); every amount (BT-131, BG-23, BT-106…115) is derived with the same `decimal.js` half-up clone as the plausibility layer, so Layer 3 is the first oracle of the generator (the property test asserts `plausible === true` on 50 seeded random inputs with 2–4-decimal prices and fractional quantities). Numbers may be JSON numbers or numeric strings; both become `Decimal` at the boundary. Mandatory-for-XRechnung facts that the model is prone to forget are enforced by Zod refinements that cite the rule (`vatExemption` for E/AE/K/G → BR-E-10 family; `dueDate` or `payment.terms` → BR-CO-25; ≥ 3 digits in the seller phone → BR-DE-27) so the model gets a one-line fix instead of a validation report. The serializer (`toUblXml`) is a hand-written indenting builder that emits UBL 2.1 in schema order with the pinned XRechnung 3.0 CustomizationID and the Peppol billing ProfileID; there is no XML library on the write path. Allowances/charges, payee, delivery and attachments are out of scope for v0.9 (YAGNI; the plausibility layer already handles them on the read path).
- **Fail-honest contract (PRD D5) and auto-fix policy.** `generateInvoice` always runs the full internal validation and returns `{ xml, valid, plausible, findings, autoFixes, model }`; `valid` is the real verdict, the XML is returned even when invalid, and the text summary says "NOT ready to send". The deterministic auto-fix pass runs *before* serialisation and only does meaning-preserving normalisation: VAT-ID / IBAN / BIC whitespace and case, and `S` with 0 % → `Z` (BR-S-05); each fix is reported with a code. A validate-driven repair loop was deliberately not built: with amounts derived from the model, any remaining finding stems from missing or wrong business input, which must not be invented. The Java KoSIT oracle (`pnpm oracle`) is not a CI job; the in-process validator's 89/89 parity is the accepted oracle for generated files. `output_path` must be absolute and `.xml`, existing files are never overwritten without `overwrite=true`, and the tool is the only one with `readOnlyHint: false`.

## 2026-08-25 — Task 2.4 convert_invoice + HTML preview

- **D-037 Serializers are the exact inverse of the parse maps; the round trip is asserted over the whole official test suite.** `modelToUbl` (UBL 2.1 Invoice or CreditNote, chosen by BT-3) and `modelToCii` (CII D16B) are hand-written builders over the same shared XML helper as the generator, emitting elements in XSD sequence order; the XSD layer is the oracle for ordering, the parse maps for coverage. `packages/core/test/convert.test.ts` converts every parseable instance of the XRechnung test suite UBL→CII→UBL (or CII→UBL→CII) and requires the semantic model to be identical, with exactly three documented exceptions: (1) the specification identifier is pinned by the target; (2) UBL's `cac:OrderReference/cbc:ID` is mandatory, so a sales-order-only source gains BT-13 = "NA" — the parser is left untouched and the loss report surfaces it as `added`; (3) CII D16B allows a single `InvoiceReferencedDocument`, so BG-3 is truncated to the first entry (reported as `dropped`). Converted documents of valid standard-profile sources must validate; XRechnung *extension* sources are exempt from that requirement because their header totals depend on extension elements (sub-invoice lines) the core model does not carry — the loss report says so explicitly (`kind: "profile"`, also for Factur-X EXTENDED). `generate_invoice` was refactored to `InvoiceInput → InvoiceModel → modelToUbl` so there is one UBL writer; its golden XML stayed byte-identical.
- **Loss report is mechanical, not curated.** After conversion the artifact is re-parsed and its model flattened to JSON-pointer leaves; every source leaf that is missing (`dropped`) or different (`changed`) and every result leaf absent from the source (`added`) becomes an entry with the BT id looked up from `BT_MAP`, plus the profile notice above. This cannot miss a field the model knows about and never claims knowledge of fields it does not model. Targets: `extract-xml` returns the embedded XML verbatim; `xrechnung-ubl` pins the XRechnung 3.0 CustomizationID and the Peppol billing ProfileID; `cii` keeps the source identifier (EN 16931 / XRechnung ids are syntax-neutral, Factur-X ids are CII already); `html-preview` renders the model into one self-contained HTML document (inline CSS, no scripts, no external assets, all text escaped, DE/EN labels, decimal comma in DE via string formatting of `Decimal.toFixed` — no float) that will be the visual source for the ZUGFeRD PDF in Task 2.7. `convert_invoice` is the second non-read-only tool (optional `output_path`, extension checked per target, no overwrite without `overwrite=true`).

## 2026-08-26 — Task 3.1 Streamable HTTP transport + auth

- **D-044 Own Express composition instead of `createMcpExpressApp`; `express` pinned as a direct dependency.** The approved design named the SDK helper, but it hard-codes `express.json()` at the 100 kB default, which rejects every `content_base64` PDF — and HTTP exists precisely because Claude Desktop never hands attachment bytes to stdio servers (F7). `packages/server/src/http.ts` therefore composes the same pieces itself: the SDK's `localhostHostValidation()` / `hostHeaderValidation()` middleware (DNS-rebinding protection on loopback binds, identical to the helper's logic), then per route Origin check → Bearer auth → `express.json({ limit })` with the limit derived from `KONTOR_MAX_FILE_MB` (× 4/3 + 1 MiB envelope). pnpm's strict `node_modules` does not let the package import a transitive dependency, so `express` 5.2.1 (the exact version the SDK resolves) and `@types/express` 5.0.6 were added explicitly. One `StreamableHTTPServerTransport` per session (`sessionIdGenerator: randomUUID`; the map is cleaned on `onsessionclosed`, on transport `onclose` and on shutdown); the same `createServer()` factory as stdio, so the tool surface cannot diverge (asserted by a test). Auth: `Authorization: Bearer <token>` compared with `crypto.timingSafeEqual` on equal-length buffers (a length mismatch is still one constant-time branch, not a loop oracle); tokens under 16 characters are refused at start-up; HTTP mode refuses to start without a token unless `KONTOR_ALLOW_NO_AUTH=1` *and* the bind is loopback. Origin: absent → pass (non-browser clients), `http(s)://localhost|127.0.0.1|[::1](:port)` or an exact `KONTOR_ALLOWED_ORIGINS` entry → pass, else 403 — evaluated before auth so a spoofed page never learns whether a token was right. `GET /healthz` is unauthenticated and reveals only name/version/session count (Docker health check in 3.2). TLS is not implemented: the documented deployment is a reverse proxy in front of the loopback port. Errors from the body parser are rewritten into JSON-RPC-shaped bodies (413 names `KONTOR_MAX_FILE_MB`), never a stack trace. Verified by the in-process test suite (`test/http.test.ts`: token OK / 401 / 403 / DELETE → 404 / no-auth opt-in / > 100 kB PDF via `content_base64`) and by the MCP Inspector CLI over HTTP against the built `bin.js`.

## 2026-08-26 — Task 3.2 Docker

- **D-045 Image = `node:22-alpine` runtime over a `pnpm deploy --legacy --prod` tree, built on the native platform; GHCR publishing waits for 3.6.** The build stage is pinned to `$BUILDPLATFORM` because the output is pure JavaScript — the arm64 image differs from amd64 only in its base layers, so CI never runs `tsc` or `pnpm install` under QEMU (which would turn a two-minute job into a fifteen-minute one). pnpm 10's default `deploy` requires `inject-workspace-packages=true`, which would change how every developer's workspace is linked; the documented `--legacy` implementation produces the same self-contained tree (server + `@kontor-mcp/core` + `@kontor-mcp/rules` with its `files`-listed artefacts, fonts and ICC profile; 68 MB, the largest dependency being pdf-lib) without touching the workspace. `node:22-alpine` over `-slim`/distroless: 71 MB total on arm64, a shell for debugging, no native modules to worry about. The container defaults to `KONTOR_TRANSPORT=http` on `0.0.0.0` (required for `-p`), so the no-auth opt-in is unreachable there and the process exits 2 with a clear message when `KONTOR_AUTH_TOKEN` is missing; the health check hits `/healthz` on 127.0.0.1 with Node's own `fetch`, so no curl/wget is needed in the image. Three HTTP additions were made rather than deferred because the smoke test surfaced them: the Inspector CLI never sends `DELETE`, so sessions would accumulate forever → idle reaper (`KONTOR_SESSION_IDLE_MINUTES`, default 30, unref'd timer) plus a concurrency cap (`KONTOR_MAX_SESSIONS`, default 100 → 503 + `Retry-After`); and `KONTOR_ALLOWED_HOSTS` so a proxied deployment keeps Host-header validation (the list is always merged with the loopback names; without a list on a non-loopback bind the SDK's own behaviour — no Host check, token is the guard — applies and is documented). The CI job builds both platforms with `push: false` and GHA layer caching, loads the amd64 image, asserts size < 300 MB, non-root uid, refusal without a token, Docker `healthy`, 401 on a raw POST, then drives the MCP Inspector CLI over HTTP with the token: `tools/list` must return exactly 8 tools and `validate_invoice` on the bundled valid / broken samples must return `valid` / `invalid`; finally `docker stop` exercises SIGTERM. Pushing to `ghcr.io/dashankanadeeshandesilva/kontor-mcp` on tags is prepared conceptually but not wired — it is an owner-gated publish step (Task 3.6).

## 2026-08-26 — Task 3.3 kontor-agent CLI

- **D-046 The agent loop is the Anthropic SDK's Tool Runner over the SDK's own MCP bridge; the CLI adds only connection, trace and exit codes.** `@anthropic-ai/sdk` 0.120.0 ships `helpers/beta/mcp` (`mcpTools(tools, mcpClient)`), which converts MCP tool definitions to runnable tools 1:1 — the JSON Schemas the server publishes are exactly what Claude sees, so the CLI cannot drift from the server's contract and there is no hand-written `while (stop_reason === "tool_use")` loop to maintain.
